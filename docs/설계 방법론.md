# MoongCare(뭉케어) 설계와 개발 방법론

> 이 문서는 두 가지를 설명한다: (1) 서버가 왜 이런 구조로 설계됐는지, (2) 그 설계와 구현 과정에서 Claude Code의 `superpowers` 스킬셋이 실제로 어떻게 쓰였고 무엇을 얻었는지.

---

## 1. 프로젝트 개요

'뭉이' 캐릭터와 음성으로 대화하며 감정을 분석하고, 대화 종료 시 자동으로 일기를 생성해주는 FastAPI 백엔드. STT(SenseVoice) → SER(emotion2vec) → LLM 대화(OpenAI) → TTS(OpenAI gpt-4o-mini-tts) → 일기 생성(OpenAI)까지 하나의 서버로 묶는다. 텍스트가 아니라 **목소리 신호 자체**에서 감정을 읽어낸다는 점이 핵심 특징이다.

---

## 2. 아키텍처 설계

### 2.1 전체 흐름

```
클라이언트
  └─ POST /api/v1/voice/analyze (session_id, webm 오디오)
       webm→wav(ffmpeg) → [STT ‖ SER ‖ pitch 분석 병렬 실행] → 세션 메모리에 turn 추가
       응답: { transcript, emotions, pitch_mean, pitch_std }
  └─ POST /api/v1/chat/reply (session_id, transcript, emotions)
       세션 히스토리 로드 → OpenAI 호출(감정 반영 프롬프트) → assistant turn 기록
       응답: { reply_text }
  └─ POST /api/v1/tts (text, session_id, voice)
       세션 최근 user 감정 → 톤 instruction 매핑 → OpenAI gpt-4o-mini-tts 호출
       → wav 바이너리
  (위 3단계를 대화 턴 수만큼 반복)
  └─ POST /api/v1/session/end (session_id)
       누적 감정 평균 + dominant_emotion 계산 (세션은 안 지움)
  └─ POST /api/v1/diary/generate (session_id)
       세션 히스토리+평균감정으로 OpenAI가 1인칭 일기 + 한줄요약 생성
       → MySQL 저장 → 세션 메모리 정리(여기서만 세션이 삭제됨)
```

### 2.2 기술 스택

| 영역 | 사용 기술 | 선택 이유 |
|---|---|---|
| 웹 프레임워크 | FastAPI + uvicorn | 비동기 처리, 자동 API 문서화 |
| STT | SenseVoice (funasr) | 한국어 음성 → 텍스트, 로컬 오픈소스 |
| SER (감정분석) | emotion2vec (funasr) | 음성 신호 자체에서 감정 추출 (텍스트 기반 아님) |
| 피치 분석 | pyworld | F0 평균/표준편차로 감정판단 신뢰도 보조지표 |
| LLM | OpenAI Chat Completions | 감정 반영 대화 응답 + 일기/요약 생성 |
| TTS | OpenAI `gpt-4o-mini-tts` | 감정 기반 톤 instructions 가능 |
| DB | MySQL + SQLAlchemy | 대화 종료 시 확정된 일기만 영구 저장 |
| 환경 | Python 3.10, GPU 8GB | STT/SER 실시간 추론용 (TTS는 API라 GPU 불필요) |

### 2.3 핵심 설계 결정과 이유

**GPU 자원 직렬화** — GPU 8GB 카드 한 장에서 STT/SER가 자원을 두고 충돌하지 않도록 `asyncio.Lock`(`stt_lock`/`ser_lock`)을 `app.state`에 두고 추론 구간을 직렬화한다. blocking 추론 호출은 `run_in_threadpool`로 감싸 이벤트 루프가 막히지 않게 한다.

**TTS를 OpenAI API로 전환** — 원래 로컬 CosyVoice3(zero-shot voice clone, GPU 상주 모델)를 썼으나, GPU 한 장에 모델 3개(STT/SER/TTS)를 얹고 락으로 직렬화하는 부담을 덜기 위해 API 호출로 교체했다. `instructions` 파라미터로 세션의 최근 user 감정에 맞춰 톤을 자연어로 지시할 수 있는 것도 장점. 대신 커스텀 목소리 clone은 포기하고 OpenAI preset 목소리를 쓴다.

**세션은 메모리, 확정본만 DB** — 데모/발표용 로컬 단일 프로세스 환경 전제. 매 턴 DB를 왕복하는 대신 프로세스 메모리에 두고, 대화가 끝나 일기로 확정될 때만 MySQL에 쓴다.

**감정 라벨 정규화** — emotion2vec 원본 출력은 `"生气/angry"`처럼 중국어가 섞인 라벨이라, 턴마다 감정을 누적 합산하려면 영어 고정 키가 필요해서 파싱 후 dict로 변환한다 (`services/ser_service.py`).

**STT 태그 제거 & 무음 가드** — SenseVoice 원본 출력에 언어/감정/이벤트 태그가 붙어 나오므로 정규식으로 제거하고, 침묵/잡음이 짧은 무의미 텍스트(`"."` 등)로 인식되면 OpenAI 호출 자체를 스킵해 토큰 낭비와 엉뚱한 응답을 막는다.

설계 근거의 원본은 `docs/superpowers/specs/`, 구현 계획의 원본은 `docs/superpowers/plans/`에 그대로 남아있다.

## 3. Superpowers를 활용한 개발 방법론

"AI한테 던지고 코드를 받는" 방식이 아니라, **AI가 설계 문서를 먼저 쓰게 하고, 그 문서를 기준으로 테스트-먼저 구현을 강제**하는 프로세스로 진행했다 (Claude Code + `superpowers` 스킬셋). 이 서버는 이 프로세스로 총 3개 계획, 30개 태스크, 53개 커밋을 거쳐 만들어졌다.

### 3.1 기본 사이클

| 단계 | 스킬 | 하는 일 | 산출물 |
|---|---|---|---|
| 1 | `brainstorming` | 코드 짜기 전, 질문 하나씩 던지며 요구사항 범위를 좁힘 | (문서화 전 단계, 합의만) |
| 2 | `writing-plans` — 스펙 | API 응답 형태·세션 구조·에러 정책을 확정. 수치가 필요하면 스크립트로 실측 후 반영 | `docs/superpowers/specs/*.md` |
| 3 | `writing-plans` — 태스크 분해 | 스펙을 실행 단위로 쪼갬. 결합도를 보고 순차/병렬 진행 방식을 결정 | `docs/superpowers/plans/*.md` |
| 4 | `executing-plans` 또는 `subagent-driven-development` | 태스크 1개 = 실패하는 테스트 작성 → 구현 → 통과 확인 → 그 태스크만 커밋 | git 커밋 1개당 태스크 1개 |

이 사이클을 프로젝트 안에서 세 번 돌렸다. 순서대로 자세히.

### 3.2 ① 초기 서버 구축 — 20개 태스크

스펙: `docs/superpowers/specs/2026-07-18-moongcare-server-design.md`
계획: `docs/superpowers/plans/2026-07-18-moongcare-server-implementation.md`

태스크 20개를 기능 단위로 한 줄씩 쪼갰다:

```
Task 1  환경 설정 (torch/CosyVoice 의존성, ffmpeg)
Task 2  프로젝트 스캐폴딩 — config, .env.example, health-check main.py
Task 3  utils/text_parser.py — SenseVoice 태그 제거
Task 4  utils/audio_converter.py — ffmpeg로 webm→wav
Task 5  models/ — pydantic 요청/응답 스키마
Task 6  database/connection.py + database/diary_repository.py
Task 7  services/emotion_session.py — 인메모리 세션 저장소
Task 8  services/ser_service.py — emotion2vec 래퍼
Task 9  services/stt_service.py — SenseVoice 래퍼
Task 10 services/voice_service.py — STT+SER 병렬 실행
Task 11 services/tts_service.py — CosyVoice2 zero-shot 래퍼 (이후 Task ③에서 OpenAI로 교체)
Task 12 services/openai_client.py + services/chat_service.py
Task 13 services/diary_service.py + services/summary_service.py
Task 14 routers/voice.py — POST /api/v1/voice/analyze
Task 15 routers/chat.py — POST /api/v1/chat/reply
Task 16 routers/tts.py — POST /api/v1/tts
Task 17 routers/session.py — POST /api/v1/session/end
Task 18 routers/diary.py — POST /api/v1/diary/generate
Task 19 main.py에 전부 연결 (실제 모델 로딩)
Task 20 수동 End-to-End 검증 스크립트
```

**진행 방식이 태스크 중간에 바뀌었다.** Task 1~8은 `subagent-driven-development`로 진행 — 태스크마다 brief(지시서) 작성 → 서브에이전트가 구현 → report(결과 보고) 수령 → git diff로 리뷰, 이 네 단계를 거쳤다. Task 9부터는 `routers → services → emotion_session.py`로 이어지는 결합도가 높다는 걸 확인하고 (예: `voice_service`가 `stt_service`+`ser_service`를 동시에 참조, 라우터 5개가 전부 이 체인을 통과) 서브에이전트 병렬 분배는 위험하다고 판단, `executing-plans`로 전환해 계획서 순서 그대로 직접 TDD로 구현했다. 즉 **같은 계획 안에서도 태스크 간 결합도를 보고 실행 전략 자체를 바꿨다** — 스킬을 기계적으로 끝까지 따른 게 아니라 상황 판단이 들어간 지점.

### 3.3 ② 피치(음높이) 분석 기능 추가

스펙: `docs/superpowers/specs/2026-07-19-pitch-analysis-design.md`
계획: `docs/superpowers/plans/2026-07-19-pitch-analysis-implementation.md`

새 기능이라 "이어하기"가 아니라 브레인스토밍부터 재시작. 이때 나온 핵심 질문 하나: *"떨림 수치를 API 응답에 노출만 할지, 서버의 감정 판단 로직(감정 선택·챗 응답·일기 생성)에 반영할지"* — 답은 **노출만, 판단 로직 불간섭**으로 스펙에 명시했다 (`voice_service.py`가 pitch를 계산은 하지만 `emotion_session.py`의 누적 평균에는 들어가지 않는 구조).

스펙에 적은 지표 정의도 감으로 안 쓰고 실측했다:
- `pitch_mean`: 발화 구간(유성음 프레임만) F0 평균, Hz
- `pitch_std`: 같은 구간 F0 표준편차 — 공식 jitter/shimmer는 아니고 "억양 기복" 근사치로만 사용한다고 스펙에 명시
- 무성음/무음 프레임은 통계에서 제외, 완전 무음이면 `(0.0, 0.0)` 반환

**태스크 5개**:
```
Task 1  services/pitch_service.py — pyworld 피치 분석
Task 2  services/voice_service.py — pitch를 STT/SER와 병렬 실행
Task 3  models/voice.py — VoiceAnalyzeResponse에 피치 필드 추가
Task 4  routers/voice.py — 라우터에서 4-tuple(transcript, emotions, pitch_mean, pitch_std) 반영
Task 5  수동 확인 (실제 서버로 검증)
```

테스트 계획에도 "220Hz 사인파 합성 오디오를 넣으면 `pitch_mean`이 대략 그 근처로 나오는지" 같은 실측 기반 assertion이 들어갔다 — "대충 맞겠지"가 아니라 스크립트로 돌려보고 실제로 나오는 범위를 스펙에 박아넣은 것.

### 3.4 ③ TTS를 OpenAI API로 마이그레이션 — subagent-driven-development 재사용

스펙: `docs/superpowers/specs/2026-07-20-openai-tts-emotion-design.md`
계획: `docs/superpowers/plans/2026-07-20-openai-tts-emotion.md`

**배경**: 로컬 CosyVoice3(zero-shot voice clone, GPU 상주)를 계속 쓰면 GPU 8GB 한 장에 STT+SER+TTS 세 모델을 다 올려야 해서 락 경합 부담이 컸다. 스펙 단계에서 트레이드오프를 명시적으로 적어뒀다: 커스텀 목소리 clone은 포기하고 OpenAI preset 목소리를 쓰는 대신, `instructions` 파라미터로 감정 톤을 자연어로 지시하는 능력을 얻는다.

**태스크 5개** (다시 `subagent-driven-development`로 진행 — 태스크마다 brief/report/diff 세트가 `.superpowers/sdd/`에 남아있다):
```
Task 1  emotion_session에 get_last_user_emotion(session_id) 헬퍼 추가
Task 2  TTSRequest에 session_id/voice 필드, config.py에 voice 화이트리스트 추가
Task 3  services/tts_service.py를 OpenAI 호출로 전면 재작성
Task 4  routers/tts.py를 voice 검증 + OpenAI 경로로 재작성
Task 5  main.py에서 CosyVoice 모델 로딩 제거
```

Task 1 brief의 실제 내용 예시 (TDD 지시가 얼마나 구체적으로 못박히는지):

```python
# Step 1: 실패하는 테스트를 먼저 쓴다
def test_get_last_user_emotion_returns_most_recent_user_turn():
    add_user_turn("s1", "t1", {"happy": 0.8, "sad": 0.2})
    add_assistant_turn("s1", "반가워")
    add_user_turn("s1", "t2", {"sad": 0.9, "happy": 0.1})
    assert get_last_user_emotion("s1") == {"sad": 0.9, "happy": 0.1}

# Step 2: pytest 실행 → ImportError로 실패 확인
# Step 3: 최소 구현
def get_last_user_emotion(session_id: str) -> dict[str, float] | None:
    state = SESSIONS.get(session_id)
    if state is None:
        return None
    for turn in reversed(state.turns):
        if turn.role == "user":
            return turn.emotions
    return None
# Step 4: pytest 재실행 → 11/11 통과 확인
# Step 5: 이 두 파일만 골라 커밋
```

서브에이전트가 이 brief를 받아 구현하고 남긴 report에는 "Deviations from Brief: None — brief에 적힌 그대로 구현" 항목이 명시적으로 들어간다. 계획과 실제 구현이 어긋나지 않았는지를 사람이 report 한 줄만 보고도 확인할 수 있게 만든 구조.

### 3.5 리뷰가 실수를 잡은 실제 사례

Task 2에서는 그렇게 매끄럽게 안 끝났다. 서브에이전트가 `TTSRequest` 필드 추가 작업 도중, 구현 범위와 무관한 diary 테스트 WIP 변경사항까지 실수로 같이 커밋했다. 커밋 직후 diff 리뷰 단계가 이를 "Important" 등급으로 잡아냈고, `git reset` 후 대상 커밋 범위를 `c64b4d5`로 다시 좁혀 재커밋 — WIP는 uncommitted 상태로 복원했다 (`.superpowers/sdd/progress.md` Task 2 기록, `review-aa88a45..c64b4d5.diff` / `review-aa88a45..d855e41.diff` 두 리뷰 버전이 남아있음). **AI가 짠 코드를 AI가 다시 검증하게 만드는 구조가 실제로 작동한 사례** — 사람이 매 커밋을 직접 diff로 안 봤어도 스코프 오염이 걸러졌다.

### 3.6 부수적으로 사용한 스킬

- **`claude-api`** — LLM 프로바이더를 OpenAI에서 Claude API로 바꿔보는 실험을 할 때 로드. Anthropic SDK 사용법(시스템 프롬프트가 별도 파라미터로 빠지는 것 등)을 참고해 `services/chat_service.py` 등을 수정. 이후 크레딧 문제로 다시 OpenAI로 되돌림 — 실패한 시도도 기록에 남겼다.
- **`artifact-design`** — 마이크 녹음 테스트 페이지를 처음 프로토타이핑할 때 로드. Artifact가 샌드박스 iframe이라 마이크 권한이 막혀 실제로는 로컬 `scripts/manual_test.html`로 옮겨감. 디자인 참고용으로만 남음.

### 3.7 이 방식이 남긴 것

1. **재현 가능한 설계** — 설계·계획 문서가 저장소(`docs/superpowers/`)에 그대로 남아 "왜 이렇게 만들었는지"를 코드만 봐서는 알 수 없는 부분까지 추적 가능하다.
2. **검증 기반 설계** — 스펙에 들어가는 수치(피치 기대값 등)는 감이 아니라 실측 스크립트로 확인한 뒤 문서화했다.
3. **상황에 맞춘 실행 전략 전환** — 결합도가 낮은 초반 태스크는 서브에이전트 병렬(§3.2), 결합도가 높아지면 직접 순차 TDD로 전환 — 스킬을 맹목적으로 따르지 않고 판단이 들어감.
4. **테스트로 강제된 완성도** — 태스크마다 테스트 통과가 커밋 조건이라, 18개 테스트 파일이 회귀를 방지한다.
5. **AI 검증 루프의 실효성** — subagent-driven-development의 리뷰 단계가 실제로 잘못된 커밋 범위를 잡아낸 사례가 있다 (§3.5).
